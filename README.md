# RepoRank

> 大多数 coding agent 把代码检索当成 grep。这个项目把它当成排序问题。

一个从零实现的研发提效 Agent。核心差异化在于把「代码上下文检索」按信息检索的方法论重做：稀疏检索 + 稠密检索 + 融合 + 重排 + 调用图先验，并提供完整的离线评测。

**当前进度**：W1–W5 已完成（BM25 基线、评测框架、切分实验、稠密检索、RRF 融合）。W6 重排进行中。

---

## 主结果

SWE-bench Lite，文件级定位，n=50。公开参照：BM25-Lucene 约 33.7%，Agentless 1.5 + GPT-4o 约 69.7%。

| 方案 | R@1 | R@5 | R@10 | R@20 | MRR | 耗时 |
|---|---|---|---|---|---|---|
| BM25 朴素分词 | 0.200 | 0.440 | 0.540 | 0.600 | 0.312 | 33s |
| + 代码分词器 | 0.300 | 0.620 | 0.740 | 0.800 | 0.452 | 70s |
| + 路径加权 ×3 | 0.340 | 0.640 | 0.740 | 0.820 | 0.489 | 69s |
| **+ 超参调优 (k1=1.2, ×10)** | **0.460** | 0.660 | 0.720 | 0.820 | 0.550 | 69s |
| **+ 稠密检索 (bge-small)** | 0.420 | **0.780** | **0.820** | **0.880** | **0.572** | 220s |
| **+ RRF 融合 (k=10, 权重 1:2)** | **0.500** | **0.780** | **0.840** | **0.920** | **0.629** | ~280s |
| + Cross-Encoder 重排 | | | | | | |
| + 调用图 PageRank | | | | | | |

从朴素 BM25 到当前最佳，**R@1 提升 30pt，R@5 提升 34pt，R@20 提升 32pt，MRR 提升 0.317**。

R@20 = 0.920 触及该开发集的 Oracle 融合上限（见 W5），意味着检索方法的组合已达理论最优，剩余 8% 为两路共同失败。

### 指标说明

数据集全部为单文件修改（多文件比例 0%）。此时 Recall@k 与 Hit@k 数学等价，NDCG@k 退化为 MRR 的截断形式，故仅报告 Recall 与 MRR。评测代码保留全部四项指标，以便后续迁移至 SWE-bench Verified（多文件比例约 14%）时使用。

## W1–W2：稀疏检索基线

### 代码专用分词器（+10pt R@1）

`getUserName` 在通用分词器眼里是一个词，而 issue 里写的是 "get user name"，匹配不上。本项目按驼峰、下划线、数字边界拆分标识符，同时保留原始形式供精确匹配：

```
getUserName  → [getusername, get, user, name]
HTTPResponse → [httpresponse, http, response]
user_id      → [user, id]
```

停用词表刻意保守——不能照搬 NLP 的英文停用词表，代码里 `if`/`for` 是噪声，但 `self`/`class` 在某些查询下是信号。

代价：索引耗时翻倍（33s → 70s）。这是全流程唯一一处显著的效果/成本权衡。

### 路径加权（+12pt R@1，零成本）

文件路径是极强信号——issue 提到 auth 时 `src/auth/` 下的文件大概率相关。但 `rank_bm25` 不支持多字段索引，无法做正规的 field boosting。

变通方案：**将路径 token 重复 N 次**，利用 BM25 的词频机制近似实现字段加权。

| path_boost | R@1 | MRR |
|---|---|---|
| 0 | 0.300 | 0.452 |
| 1 | 0.320 | 0.479 |
| 3 | 0.340 | 0.489 |
| 6 | 0.400 | 0.521 |
| **10** | **0.420** | **0.533** |

该近似的副作用是会改变文档长度分布，与长度归一化参数 `b` 存在交互——见下节。

### 超参调优（+12pt R@1）

初始基线使用库默认值，未经调优。这构成方法论漏洞：用未调优的基线去比较其他方案，结论不可信。

| 配置 | R@1 | R@5 | R@10 | R@20 | MRR |
|---|---|---|---|---|---|
| 原基线 `k1=1.5, b=0.75, pb=3` | 0.340 | 0.640 | 0.740 | 0.820 | 0.489 |
| `k1=1.2, b=0.5, pb=10` | 0.440 | 0.640 | 0.740 | 0.800 | 0.532 |
| **`k1=1.2, b=0.75, pb=10`** | **0.460** | **0.660** | 0.720 | **0.820** | **0.550** |

**超参交互**：单参数扫描时 `b=0.5` 优于默认 `0.75`（R@1 0.420 vs 0.340），但在 `path_boost=10` 下反转（0.440 vs 0.460）。两者调节的是同一类信号——文档长度归一化强度与路径 token 注入量——因此单参数最优不等于组合最优。

调优后的 R@1 = 0.460 比公开报告的 BM25-Lucene（33.7%）高 12pt。所有后续实验均以此为基线。

### 关键观察：召回与排序的分离

R@20 = 0.820 而 R@1 = 0.340（调优前），48pt 的差距说明多数失败是**排序问题**而非召回问题。

更重要的是：**R@20 从 W2 到 W3 结束始终恒定在 0.820**，对所有参数调整、切分策略免疫。这 18% 的硬失败是稀疏检索的机制上限，需要语义匹配才能突破。

## W3：负面结果 —— Chunk 级检索在 BM25 上无效

假设：长文件中相关函数只占一小段，整文件索引会稀释信号。切分至函数级应提升精度。

### 实验设计：为什么需要固定窗口对照组

若仅对比「整文件」与「AST 切分」，即使结果为负，也无法区分是**切分本身**有害还是**AST 这种切分方式**有害。因此引入第三组：完全不理解代码结构的固定行窗口（60 行 / 45 行步长）。

| 切分策略 | R@1 | R@5 | R@10 | R@20 | MRR | 耗时 |
|---|---|---|---|---|---|---|
| **整文件（基线）** | 0.460 | **0.660** | **0.720** | **0.820** | **0.550** | **69s** |
| 固定行窗口 | 0.380 | 0.580 | 0.680 | 0.740 | 0.473 | — |
| AST 函数级 | 0.360 | 0.600 | 0.660 | 0.740 | 0.453 | 196s |

**结论**：固定窗口与 AST 切分表现几乎一致（R@10 均为 0.680），说明性能变化源于切分动作本身，而非切分方式。AST 切分的 R@1 甚至不如朴素窗口。

没有对照组会得出「AST 不适合代码检索」这一错误结论——真实结论是「chunk 级检索不适合 BM25」，两者指向完全不同的后续动作。

### chunk → file 聚合策略

切分后一个文件对应数十个 chunk，折叠为文件分数的方式成为新的关键超参。

| 聚合方式 | R@1 | R@5 | R@10 | R@20 | R@30 | MRR |
|---|---|---|---|---|---|---|
| max | 0.360 | 0.600 | 0.640 | 0.740 | 0.780 | 0.452 |
| top3-sum | 0.360 | 0.600 | 0.680 | 0.740 | 0.780 | 0.475 |
| **sum** | **0.060** | 0.400 | 0.520 | 0.720 | **0.820** | 0.215 |

`sum` 的失败曲线是**长度偏置的教科书级证据**：R@1 = 0.060（近乎失效）但 R@30 = 0.820（追平基线）。chunk 数量多的大文件在总分上碾压小文件，正确的小文件被挤出前列但并未消失。这正是 BM25 长度归一化（`b` 参数）所要防止的偏置在文件层面的重现。

### 公平性修正

初次对比使用调优后的整文件基线 vs 未调优的 AST 方案，不公平。使用相同参数（`k1=1.2, pb=10`）重测后，差距从 −2pt 扩大至 −10pt：调参对整文件有效、对 chunk 无效，负面结论更加稳固。

### 处理方式

切分能力保留于代码中，默认关闭。稠密检索存在 512 token 输入上限，切分在 W4 中是必需品而非选项——同一技术在不同检索范式下价值相反。

## W4：稠密检索

目标是 W2/W3 反复确认的那 18% 硬失败：这些实例的 gold 文件与 issue 无共同词项，BM25 原理上无解。

### 结果（n=50, AST 切分）

| 方案 | R@1 | R@5 | R@10 | R@20 | MRR | 耗时 |
|---|---|---|---|---|---|---|
| BM25-tuned（基线） | **0.460** | 0.660 | 0.720 | 0.820 | 0.550 | 69s |
| **bge-small (33M)** | 0.420 | **0.780** | **0.820** | **0.880** | **0.572** | 220s |
| MiniLM (22M) | 0.380 | 0.620 | 0.720 | 0.800 | 0.488 | ~250s |
| MiniLM 全语料 | 0.360 | 0.600 | 0.720 | 0.780 | 0.463 | 907s |

**互补的性能曲线**：BM25 的 Top-1 精度更高（0.460 vs 0.420），稠密检索的整体召回显著更高（R@5 +12pt，R@10 +10pt，R@20 +6pt）。两者分别擅长精准定位与广覆盖。

**模型选择比模型规模更重要**：bge-small（33M）全面优于 MiniLM（22M），MRR +0.084，参数量仅多 50%。

### 互补性验证（R@20 口径）

| | bge-small | MiniLM |
|---|---|---|
| 两者共同失败 | 4 | 5 |
| 稠密救回（BM25 失败） | **5** | 4 |
| 稠密丢失（BM25 成功） | **2** | 6 |
| 净收益 | **+3** | −2 |
| **Oracle 融合上限 R@20** | **0.920** | 0.900 |

融合上限比最佳单一方案（0.880）高 4pt。更值得注意的是：更换嵌入模型不仅提升单点性能，还**改变了互补结构**——MiniLM 下净收益为负，bge-small 下转正。这是选择 bge-small 的第二个理由。

### 成本控制

全语料编码在 SWE-bench 规模下不可行（django 快照切分后上万 chunk）。实现了两阶段方案：

- `DenseRetriever` — 全语料编码，用于度量方法上限
- `PrefilteredDenseRetriever` — BM25 粗筛 Top-N 文件后仅编码候选，成本降低一到两个数量级

粗筛的召回率即稠密层的性能天花板，由 `prefilter_recall()` 单独报告，避免数字虚高。

配合按内容哈希的磁盘缓存，重复实验近乎免费。

### 硬件约束

Qwen3-Embedding-0.6B（600M）在 MacBook Air（MPS）上不可行：进程因内存压力被拖至停滞，系统 swapout 达 570 万次，`kernel_task` 占用 20% CPU。

这不是实验疏漏而是真实工程约束。coding agent 的检索层存在实时性要求，大模型 embedding 的延迟与内存成本在多数部署场景下同样不可接受。本项目因此将稠密检索限定在 100M 参数以内。

### 样本量教训

在前 20 条子集上，bge-small 的 R@20 落后 BM25 5pt；扩展至 50 条后反超 6pt。BM25 自身在 20 条上 R@1 = 0.600、在 50 条上仅 0.460——子集难度分布差异显著。所有对比均需同口径，小样本结论不可依赖。

## W5：RRF 融合 —— 触及 Oracle 上限

两路检索粒度不同（BM25 文件级最优，稠密受 512 token 限制必须 chunk 级），因此融合只能在**排序结果层面**进行。这恰是 RRF 的适用场景：它只消费排序列表，不关心文档粒度。

### 健全性检查

融合器内部对语料做粒度分流（chunk 合并回文件给 BM25，原始 chunk 给稠密）。单路模式用于验证分流正确：

| | 独立运行 | 融合器内部 | 差 |
|---|---|---|---|
| BM25 R@20 / R@30 | 0.820 / 0.840 | 0.820 / 0.840 | **0** |
| BM25 R@1 | 0.460 | 0.440 | −2pt |

召回集合完全一致，分流正确。头部 2pt 的差异来自 chunk 上下文头注释（`# file:` / `# symbol:`）在合并时按 chunk 数重复，构成非受控的额外路径加权。后续融合结果均对照 0.440 这一内部基线。

### 首轮失败：照搬论文参数不适用

使用 RRF 原论文推荐的 `k=60`，融合**完全没有兑现互补性**：

| 方案 | R@1 | R@5 | R@10 | R@20 | MRR |
|---|---|---|---|---|---|
| bm25only | 0.440 | 0.660 | 0.700 | 0.820 | 0.534 |
| denseonly | 0.420 | **0.780** | **0.820** | 0.880 | 0.572 |
| rrf k=60 | 0.420 | 0.760 | 0.800 | 0.880 | 0.576 |

失败分析显示：融合净损失 2 例、独有成功 0 例，`0.920 − 2/50 = 0.880` 恰好等于实测值。丢失的两例正是「稠密救回、BM25 失败」的实例。

**可量化的机制**：RRF 分数为 `1/(k + rank)`。在 `k=60`、候选池 100 的配置下，头尾分数比仅 2.6 倍：

| 文档情况 | RRF 分数 |
|---|---|
| 稠密排第 1，BM25 未召回 | `1/61` = 0.01639 |
| 两路均排第 50 | `2/110` = **0.01818** |

被稠密排在首位的文档输给了两路都排在第五十位的文档。**k 过大使「出现在多个列表中」压倒「排名靠前」，系统性地惩罚互补性本身——而互补正是融合的前提。** `k=60` 源自 TREC 场景，那里的候选池通常上千，尺度并不匹配。

### 参数扫描与组合

| 方案 | R@1 | R@5 | R@10 | R@20 | MRR |
|---|---|---|---|---|---|
| rrf k=60（论文默认） | 0.420 | 0.760 | 0.800 | 0.880 | 0.576 |
| rrf k=30 | 0.420 | 0.760 | 0.800 | 0.880 | 0.578 |
| rrf k=10 | 0.440 | 0.760 | 0.820 | 0.900 | 0.597 |
| rrf 权重 1:2 (k=60) | 0.500 | 0.760 | 0.800 | 0.880 | 0.620 |
| rrf 权重 1:3 (k=60) | 0.480 | 0.760 | 0.820 | 0.900 | 0.614 |
| **rrf k=10 + 权重 1:2** | **0.500** | **0.780** | **0.840** | **0.920** | **0.629** |
| rrf k=5 + 权重 1:2 | 0.480 | 0.780 | 0.840 | 0.920 | 0.617 |
| score fusion (min-max) | 0.480 | 0.780 | 0.800 | 0.900 | 0.618 |

**超参正交（正例）**：`k` 与权重分别单独有效，组合后收益完全保留。这与 W1–W2 中 `b` × `path_boost` 互相抵消形成对照——后者调节同一类信号，前者调节两个独立维度（名次陡峭度 vs 两路相对权重）。**超参能否叠加，取决于它们是否作用于同一机制。**

**反直觉的权重方向**：稠密检索单独的 R@1（0.420）低于 BM25（0.440），但给稠密**更高**权重反而提升融合 R@1。原因是 RRF 的 `1/(k+rank)` 是凸函数，「一路第 1、一路第 3」的总分高于「两路都第 2」——RRF 不奖励稳定的中游表现，而奖励在某一路冲进头部。因此权重应给「偶尔极准」的一路，而非「平均更准」的一路。

**RRF 优于分数融合**：min-max 归一化的 CombSUM 在 R@1、R@10、MRR 上均落后。BM25 分数无界且可能为负（高频词 IDF 为负），余弦相似度有界于 [−1, 1]，归一化引入的失真大于其保留的置信度信息。

### 结果：融合超过两路单独表现

最优配置在**每一个指标**上都优于任一单路，而非简单取二者较优值：

| | R@1 | R@5 | R@10 | R@20 | MRR |
|---|---|---|---|---|---|
| BM25 | 0.440 | 0.660 | 0.700 | 0.820 | 0.534 |
| Dense | 0.420 | 0.780 | 0.820 | 0.880 | 0.572 |
| **Fusion** | **0.500** | **0.780** | **0.840** | **0.920** | **0.629** |

R@20 = 0.920 等于 W4 计算的 Oracle 上限，融合失败集合与两路共同失败集合完全相同。**检索方法的组合已达理论最优**，剩余 4 例需要机制之外的手段。

### 局限

RRF 超参在同一批 50 条上调优，存在过拟合风险；Oracle 上限亦在同一批数据上计算。最终结论需在完整 300 条上验证。

## 方法论

### Ground truth 是免费的

SWE-bench 每条实例自带 gold patch（人类真实提交的修复）。从 unified diff 解析出被修改的文件路径，即为文件定位任务的标准答案。**不需要运行测试、不需要 Docker**，整个检索层的实验可在笔记本上完成——这是能在五周内完成数十组对照实验的前提。

### 评测的健全性检查

`gold_not_in_corpus` 单独报告。若 gold 文件被语料过滤规则误杀，那是数据构建的 bug 而非检索器的问题。不区分这两者会严重误判优化效果。

组合方法（如融合）额外提供单路模式，用于验证内部数据流未引入偏差。

### 开发集与测试集分离

超参在前 50 条开发集上调优，最终结论将在完整 300 条上报告，避免在评测集上调参导致的乐观偏差。

### 每条实例明细落盘

`per_instance.jsonl` 记录每条实例的全部指标与未召回的 gold 文件。平均分只能回答「涨了没涨」，明细才能回答「该往哪改」——W4 的互补性分析与 W5 的失败归因完全依赖这份数据，且无需重跑任何实验。

## 快速开始

```bash
pip install -r requirements.txt

# 1. 离线 fixture，验证管道
python scripts/make_fixture.py
python scripts/run_eval.py --data fixtures/sample_instances.jsonl \
    --local-corpus fixtures/mini_repo --retriever bm25 --top-k 6

# 2. 真实数据
export HF_ENDPOINT=https://hf-mirror.com
python scripts/prepare_data.py --out data/swebench_lite.jsonl

# 3. 当前最佳配置
python scripts/run_eval.py --data data/swebench_lite.jsonl \
    --retriever rrf-best --chunking ast --emb-model bge-small --limit 50

# 4. 复现任一消融实验
python scripts/run_eval.py --data data/swebench_lite.jsonl \
    --retriever bm25-naive --limit 50          # 朴素分词
python scripts/run_eval.py --data data/swebench_lite.jsonl \
    --retriever bm25-sum --chunking ast --limit 50   # sum 聚合的长度偏置
python scripts/run_eval.py --data data/swebench_lite.jsonl \
    --retriever rrf --chunking ast --emb-model bge-small --limit 50   # k=60 论文默认值
```

## 目录结构

```
reporank/
├── data/
│   ├── swebench.py     # 实例加载 + gold patch 解析
│   └── repo.py         # 仓库快照导出 + 语料构建
├── index/
│   ├── tokenizer.py    # 代码感知分词器
│   ├── chunker.py      # 三种切分策略（file / window / ast）
│   └── embedder.py     # 编码器 + 磁盘缓存 + 设备自适应
├── retrieval/
│   ├── base.py         # Retriever 接口 + chunk→file 聚合
│   ├── bm25.py         # 稀疏检索
│   ├── dense.py        # 稠密检索 + 两阶段粗筛
│   └── fusion.py       # RRF / 分数融合 + 混合检索器
└── eval/
    ├── metrics.py      # Recall@k / Precision@k / MRR / NDCG@k
    └── runner.py       # 评测主循环 + 结果落盘
```

新增检索方案只需实现 `Retriever` 接口并在 `scripts/run_eval.py` 的注册表加一行。从文件级换到函数级、再到向量检索、再到多路融合，**评测层代码零改动**——这源于 W1 就钉死的契约：`Document.path` 恒为文件路径，与索引粒度无关。

### 当前瓶颈

召回已达组合方法的理论上限（R@20 = 0.920 = Oracle）。**剩余 42pt 的 R@1–R@20 差距完全是排序问题**：正确文件已被召回，只是没排到前面。这是 W6 重排层的全部目标，也是 Cross-Encoder 相比 Bi-Encoder 的优势区间——query 与文档拼接后过完整 attention，代价是无法离线预计算，因此只能用于候选重排而非初检。

### 未来工作

学习型稀疏检索（SPLADEv2、TILDEv2）是潜在方向，但现有模型均在自然语言语料上训练，其 WordPiece 切分会将 `getUserName` 拆为 `get ##user ##name`，与本项目的代码专用分词器冲突；推理成本亦与 100M 级稠密模型相当。在重排层的收益空间耗尽前，暂不引入。

### 待验证的核心假设

检索召回率与端到端修复成功率**并非单调正相关**。SWE-bench 原论文指出增大检索窗口会提升召回，但因无关上下文干扰而降低端到端表现。W12 将量化这个拐点。
